Docker Compose — L'Infrastructure en Un Fichier

Docker, c'est quoi ?

Imaginez un conteneur maritime : peu importe ce qu'il y a dedans (vêtements, électronique, nourriture), le conteneur a toujours la même forme et se charge sur n'importe quel bateau de la même manière. Docker fonctionne pareil pour les logiciels : chaque application (base de données, serveur web, outil de monitoring) est emballée dans un « conteneur » standardisé qui tourne de manière identique sur n'importe quel serveur.

Docker Compose va plus loin : c'est un fichier unique (docker-compose.yml) qui décrit tous vos conteneurs et comment ils communiquent entre eux. Un seul docker compose up -d et tout démarre.

Le fichier complet

TimescaleDB — La Base de Données du Trader

Pourquoi TimescaleDB et pas PostgreSQL classique ?

TimescaleDB est une extension PostgreSQL spécialisée dans les données temporelles (séries de prix, ticks, trades). Elle est 100% compatible SQL — tout ce que vous savez faire en PostgreSQL fonctionne — mais ajoute trois super-pouvoirs :

Hypertables
Les tables normales stockées en un seul bloc. Les hypertables découpent automatiquement les données par période (chunks). Résultat : les requêtes sur les dernières 24h sont ultra-rapides car elles ne lisent qu'un seul chunk.
Continuous Aggregates
Des « vues matérialisées » qui se mettent à jour automatiquement. Au lieu de recalculer votre P&L à chaque requête, TimescaleDB maintient le résultat pré-calculé en temps réel.
Compression native
Les données de plus de X jours sont automatiquement compressées (90-95% de réduction). Vos années d'historique tiennent sur un petit SSD.

Schéma SQL complet

init.sql — Tables principales
-- ========================================
-- Schema: trading monitoring stack
-- ========================================

-- Extension TimescaleDB
CREATE EXTENSION IF NOT EXISTS timescaledb;

-- 1. Table des trades exécutés
CREATE TABLE trades (
    time        TIMESTAMPTZ NOT NULL,
    symbol      TEXT        NOT NULL,
    side        TEXT        NOT NULL,  -- 'buy' ou 'sell'
    quantity    NUMERIC     NOT NULL,
    price       NUMERIC     NOT NULL,
    commission  NUMERIC     DEFAULT 0,
    strategy    TEXT,                   -- 'momentum', 'mean_reversion', etc.
    order_id    TEXT,                   -- ID du broker
    notes       TEXT
);
SELECT create_hypertable('trades', 'time');

-- 2. Table des positions ouvertes
CREATE TABLE positions (
    time            TIMESTAMPTZ NOT NULL,
    symbol          TEXT        NOT NULL,
    quantity        NUMERIC     NOT NULL,
    avg_price       NUMERIC     NOT NULL,
    current_price   NUMERIC,
    unrealized_pnl  NUMERIC,
    strategy        TEXT
);
SELECT create_hypertable('positions', 'time');

-- 3. Table des données de marché (OHLCV)
CREATE TABLE market_data (
    time    TIMESTAMPTZ NOT NULL,
    symbol  TEXT        NOT NULL,
    open    NUMERIC,
    high    NUMERIC,
    low     NUMERIC,
    close   NUMERIC,
    volume  BIGINT
);
SELECT create_hypertable('market_data', 'time');

-- 4. Table des métriques de risque
CREATE TABLE risk_metrics (
    time            TIMESTAMPTZ NOT NULL,
    equity          NUMERIC,          -- Valeur totale du portefeuille
    cash            NUMERIC,
    daily_pnl       NUMERIC,
    max_drawdown    NUMERIC,          -- Drawdown courant en %
    open_positions  INTEGER,
    total_exposure  NUMERIC,          -- Exposition totale en valeur
    largest_position NUMERIC,         -- Plus grosse position en %
    broker_latency  NUMERIC           -- Latence API broker en ms
);
SELECT create_hypertable('risk_metrics', 'time');

-- Index pour les requêtes fréquentes
CREATE INDEX idx_trades_symbol ON trades (symbol, time DESC);
CREATE INDEX idx_positions_symbol ON positions (symbol, time DESC);
CREATE INDEX idx_market_data_symbol ON market_data (symbol, time DESC);

-- Compression automatique après 7 jours
ALTER TABLE market_data SET (
    timescaledb.compress,
    timescaledb.compress_segmentby = 'symbol',
    timescaledb.compress_orderby = 'time DESC'
);
SELECT add_compression_policy('market_data', INTERVAL '7 days');

Continuous Aggregates — le P&L automatique

SQL — Agrégats continus
-- OHLCV 1 minute (pour données tick/intraday)
CREATE MATERIALIZED VIEW ohlcv_1min
WITH (timescaledb.continuous) AS
SELECT
    time_bucket('1 minute', time) AS bucket,
    symbol,
    first(open, time) AS open,
    max(high)         AS high,
    min(low)          AS low,
    last(close, time) AS close,
    sum(volume)       AS volume
FROM market_data
GROUP BY bucket, symbol;

-- P&L quotidien par stratégie
CREATE MATERIALIZED VIEW daily_pnl
WITH (timescaledb.continuous) AS
SELECT
    time_bucket('1 day', time)  AS day,
    strategy,
    sum(CASE WHEN side = 'sell' THEN quantity * price
             WHEN side = 'buy'  THEN -quantity * price
        END)                    AS realized_pnl,
    count(*)                    AS trade_count,
    sum(commission)             AS total_commissions
FROM trades
GROUP BY day, strategy;

-- Rafraîchissement automatique
SELECT add_continuous_aggregate_policy('ohlcv_1min',
    start_offset    => INTERVAL '3 hours',
    end_offset      => INTERVAL '1 minute',
    schedule_interval => INTERVAL '1 minute'
);

SELECT add_continuous_aggregate_policy('daily_pnl',
    start_offset    => INTERVAL '3 days',
    end_offset      => INTERVAL '1 hour',
    schedule_interval => INTERVAL '1 hour'
);

Continuous Aggregates, expliqué simplement

Imaginez un tableau Excel qui se recalcule tout seul quand vous ajoutez des données. Au lieu de relancer la formule SOMME() à chaque fois, Excel maintiendrait le résultat à jour automatiquement en arrière-plan. C'est exactement ce que font les Continuous Aggregates : elles pré-calculent vos résumés (P&L quotidien, OHLCV 1 minute, etc.) et les mettent à jour dès qu'un nouveau trade ou une nouvelle bougie arrive.

Résultat : vos dashboards Grafana répondent en millisecondes, même avec des millions de lignes d'historique.

Prometheus + Alertmanager — Le Système Nerveux

Comment ça marche

Prometheus fonctionne en mode pull : toutes les 15 secondes, il interroge vos services (« hey, quelles sont tes métriques ? ») et enregistre les réponses dans sa base de données interne. Si une métrique dépasse un seuil que vous avez défini (drawdown > 5%, latence > 200ms), Alertmanager prend le relais et envoie une notification sur Discord.

Prometheus
Scrape toutes les 15 secondes. Stocke 90 jours d'historique. Langage de requête PromQL intégré.
Node Exporter
Agent léger qui expose CPU, RAM, disque, réseau de votre serveur de trading.
Alertmanager
Reçoit les alertes de Prometheus, les déduplique, les route vers Discord par sévérité.
Textfile Collector
Vos scripts écrivent des métriques dans un fichier. Node Exporter les expose à Prometheus. Zéro code serveur.

Métriques custom pour le trading

En plus des métriques système (CPU, RAM), vous allez exposer des métriques spécifiques au trading via le textfile collector de Node Exporter. Votre stratégie écrit un fichier .prom après chaque cycle :

update_metrics.sh — Script de mise à jour des métriques
#!/bin/bash
# Ce script est appelé par votre stratégie après chaque cycle
# Il écrit les métriques dans un fichier que node_exporter expose

METRICS_DIR="/var/lib/node_exporter/textfile_collector"
METRICS_FILE="${METRICS_DIR}/trading.prom"

cat > "${METRICS_FILE}" <<EOF
# HELP trading_open_positions Nombre de positions ouvertes
# TYPE trading_open_positions gauge
trading_open_positions ${OPEN_POSITIONS}

# HELP trading_daily_pnl P&L du jour en dollars
# TYPE trading_daily_pnl gauge
trading_daily_pnl ${DAILY_PNL}

# HELP trading_broker_latency_ms Latence API broker en ms
# TYPE trading_broker_latency_ms gauge
trading_broker_latency_ms ${BROKER_LATENCY}

# HELP trading_max_drawdown_percent Drawdown max courant en %
# TYPE trading_max_drawdown_percent gauge
trading_max_drawdown_percent ${MAX_DRAWDOWN}

# HELP trading_equity Valeur totale du portefeuille
# TYPE trading_equity gauge
trading_equity ${EQUITY}

# HELP trading_total_exposure Exposition totale (somme positions)
# TYPE trading_total_exposure gauge
trading_total_exposure ${TOTAL_EXPOSURE}

# HELP trading_largest_position_pct Plus grosse position en %
# TYPE trading_largest_position_pct gauge
trading_largest_position_pct ${LARGEST_POSITION}
EOF

Règles d'alerte trading

alert_rules.yml — Alertes critiques
groups:
  - name: trading_alerts
    rules:
      # CRITIQUE: Drawdown élevé
      - alert: HighDrawdown
        expr: trading_max_drawdown_percent > 5
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Drawdown > 5% ({{ $value }}%)"
          description: "Le drawdown dépasse le seuil critique."

      # WARNING: Position trop concentrée
      - alert: PositionTooLarge
        expr: trading_largest_position_pct > 10
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Position > 10% du portefeuille ({{ $value }}%)"

      # WARNING: Latence broker élevée
      - alert: BrokerLatencyHigh
        expr: trading_broker_latency_ms > 200
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "Latence broker > 200ms ({{ $value }}ms)"

      # KILL SWITCH: Perte quotidienne limite
      - alert: DailyLossLimit
        expr: trading_daily_pnl < -1000
        for: 0m
        labels:
          severity: critical
          action: kill_switch
        annotations:
          summary: "KILL SWITCH: Perte > $1000 ({{ $value }})"
          description: "Perte quotidienne limite atteinte. Arrêt immédiat."

  - name: system_alerts
    rules:
      # CPU surchargé
      - alert: HighCpuUsage
        expr: 100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) > 85
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "CPU > 85% ({{ $value }}%)"

      # Disque presque plein
      - alert: DiskSpaceLow
        expr: (node_filesystem_avail_bytes / node_filesystem_size_bytes) * 100 < 10
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Espace disque < 10%"

Attention au Kill Switch

L'alerte DailyLossLimit a un délai de 0 seconde (for: 0m). Dès que la perte quotidienne dépasse $1000, l'alerte se déclenche instantanément. Combinez-la avec un webhook Discord qui exécute un script de fermeture de positions (voir section Discord ci-dessous).

Grafana — Les Yeux du Trader

Grafana transforme vos données brutes (TimescaleDB + Prometheus) en dashboards visuels interactifs. Vous pouvez créer n'importe quel graphique, et configurer des alertes de secours (en plus de celles de Prometheus).

Les 4 dashboards essentiels

1. P&L Dashboard
Courbe d'équité (equity curve), rendements journaliers en barres, P&L cumulé par stratégie, ratio de Sharpe glissant sur 30 jours. Le dashboard que vous regardez le matin.
2. Positions Dashboard
Tableau des positions ouvertes avec P&L non réalisé, répartition sectorielle en camembert, jauge d'exposition totale. Mise à jour en temps réel.
3. Risk Dashboard
Jauge de drawdown (vert/orange/rouge), Value at Risk, heatmap de corrélation entre positions, concentration du portefeuille. Le dashboard de survie.
4. System Health
CPU, RAM, latence API broker, uptime, erreurs API, espace disque. Si votre serveur tombe, vos trades sont en danger.

Créer votre premier dashboard — pas à pas

  1. Connexion : Ouvrez http://localhost:3000, connectez-vous (admin / votre mot de passe)
  2. Data Source : Menu → Connections → Add data source → Prometheus → URL = http://prometheus:9090 → Save & Test
  3. Deuxième Data Source : Add data source → PostgreSQL → Host = timescaledb:5432, Database = trading, User = trader → Save & Test
  4. Nouveau Dashboard : + → Dashboard → Add visualization
  5. Premier panel : Data source = PostgreSQL, Query = SELECT day AS time, SUM(realized_pnl) OVER (ORDER BY day) AS cumulative_pnl FROM daily_pnl GROUP BY day ORDER BY day
  6. Personnalisation : Type = Time series, Titre = « Equity Curve », couleur verte, remplissage sous la courbe
  7. Sauvegarde : Bouton « Save » en haut à droite

Approche 1 : Webhooks (le plus simple)

Un webhook Discord est une URL unique qui accepte des messages POST. Votre stratégie envoie un message à cette URL et il apparaît dans le canal. Zéro installation, zéro bot à gérer.

Python — Notification de trade via webhook
import requests
import json
from datetime import datetime

WEBHOOK_URL = "https://discord.com/api/webhooks/VOTRE_ID/VOTRE_TOKEN"

def notify_trade(symbol, side, qty, price, strategy):
    """Envoie une notification de trade sur Discord."""
    emoji = "🟢" if side == "buy" else "🔴"
    total = qty * price

    embed = {
        "embeds": [{
            "title": f"{emoji} {side.upper()} {symbol}",
            "color": 0x059669 if side == "buy" else 0xdc2626,
            "fields": [
                {"name": "Quantité",  "value": str(qty),      "inline": True},
                {"name": "Prix",      "value": f"${price:.2f}", "inline": True},
                {"name": "Total",     "value": f"${total:.2f}", "inline": True},
                {"name": "Stratégie", "value": strategy,      "inline": True},
            ],
            "timestamp": datetime.utcnow().isoformat()
        }]
    }

    requests.post(WEBHOOK_URL, json=embed)

# Exemple d'utilisation
notify_trade("AAPL", "buy", 10, 185.50, "momentum")

Approche 2 : Bot Discord (avancé)

Un bot Discord offre des commandes interactives. Vous tapez /positions et le bot répond avec vos positions actuelles. Vous tapez /kill et il ferme toutes les positions. Plus puissant que les webhooks, mais nécessite du code supplémentaire.

Python — Bot Discord avec commandes trading
import discord
from discord import app_commands
import psycopg2
import os

intents = discord.Intents.default()
client = discord.Client(intents=intents)
tree = app_commands.CommandTree(client)

ADMIN_ROLE_ID = 123456789  # Votre rôle admin Discord

def get_db():
    return psycopg2.connect(
        host="localhost", dbname="trading",
        user="trader", password=os.getenv("TSDB_PASSWORD")
    )

# /positions — Afficher les positions ouvertes
@tree.command(name="positions", description="Positions ouvertes")
async def positions(interaction: discord.Interaction):
    conn = get_db()
    cur = conn.cursor()
    cur.execute("""
        SELECT DISTINCT ON (symbol)
            symbol, quantity, avg_price, current_price,
            unrealized_pnl, strategy
        FROM positions
        ORDER BY symbol, time DESC
    """)
    rows = cur.fetchall()
    conn.close()

    if not rows:
        await interaction.response.send_message("Aucune position ouverte.")
        return

    lines = []
    for sym, qty, avg, cur_p, pnl, strat in rows:
        emoji = "🟢" if pnl >= 0 else "🔴"
        lines.append(f"{emoji} **{sym}** | {qty} @ ${avg:.2f} → ${cur_p:.2f} | P&L: ${pnl:+.2f} | {strat}")

    await interaction.response.send_message("\n".join(lines))

# /pnl — P&L du jour
@tree.command(name="pnl", description="P&L du jour")
async def pnl(interaction: discord.Interaction):
    conn = get_db()
    cur = conn.cursor()
    cur.execute("SELECT daily_pnl, equity FROM risk_metrics ORDER BY time DESC LIMIT 1")
    row = cur.fetchone()
    conn.close()
    pnl_val, equity = row if row else (0, 0)
    emoji = "🟢" if pnl_val >= 0 else "🔴"
    await interaction.response.send_message(
        f"{emoji} **P&L du jour**: ${pnl_val:+,.2f}\n💰 **Equity**: ${equity:,.2f}"
    )

Sécurité du Kill Switch

Le kill switch est la commande la plus dangereuse de votre stack. Trois protections obligatoires :

  1. Rôle admin : seuls les utilisateurs avec le rôle admin peuvent l'utiliser
  2. Confirmation en 2 étapes : /kill demande une confirmation explicite
  3. Canal restreint : la commande ne fonctionne que dans #kill-switch

Claude Code — L'Assistant IA

Claude Code est un agent IA qui tourne dans votre terminal. Il lit votre code, comprend le contexte, et peut exécuter des commandes. Pour le trading, c'est un allié puissant — à condition de connaître ses limites.

5 cas d'usage pour le trading

1. Code Review
Détecter le look-ahead bias (utiliser des données futures), l'overfitting (trop de paramètres), les erreurs de slippage/commission dans vos stratégies.
2. Post-Mortem
Après un mauvais trade ou un crash, Claude Code analyse les logs et génère un rapport structuré : chronologie, cause racine, actions correctives.
3. Génération de Tests
Créer des tests unitaires pour vos fonctions de calcul (P&L, sizing, signaux), des tests d'intégration pour le pipeline de données, des tests de régression.
4. Analyse de Logs
Chercher des anomalies dans des milliers de lignes de logs : ordres rejetés, latence soudaine, écarts de prix, disconnexions broker.
5. Documentation
Générer la documentation de vos stratégies, du schema de base de données, des procédures d'urgence.

Exemples de prompts pour le trading

Prompt — Review d'une stratégie
# Lancer depuis le dossier de votre stratégie
claude "Review ma stratégie de trading dans strategy.py.
Vérifie spécifiquement :

Limites — ce que Claude Code ne doit PAS faire

Claude Code est un assistant, pas un oracle financier. Règles d'or :

  • Ne jamais lui faire exécuter de trades — il génère du code, il ne prend pas de décisions d'investissement
  • Vérifier les calculs financiers — les modèles IA peuvent faire des erreurs subtiles de mathématiques financières (annualisation, composition, etc.)
  • Ne pas lui confier vos clés API broker — travaillez en environnement sandbox/paper trading
  • Valider les tests générés — un test qui passe ne veut pas dire que la logique est correcte

Agents Autonomes — L'Automatisation Intelligente

Au-delà de Claude Code utilisé manuellement, il est possible d'automatiser certaines tâches de monitoring avec des agents IA autonomes : des scripts qui tournent en arrière-plan, analysent les données, et agissent selon des règles prédéfinies.

Cas d'usage légitimes

Rapports automatiques
Chaque soir, un agent génère un résumé de la journée (P&L, positions, événements) et le publie sur Discord.
Alertes proactives
Un agent surveille les earnings calendars, les décisions Fed, et vous prévient si un événement impacte vos positions.
Collecte de données
Un agent exécute des scripts de collecte (prix, volumes, sentiment) à intervalles réguliers et alimente TimescaleDB.
Maintenance
Compression de données anciennes, nettoyage de logs, vérification d'intégrité de la base, backup automatisé.

Exemple : rapport quotidien automatisé

daily_report.sh — Cron job à 22h00
#!/bin/bash
# Exécuté tous les soirs à 22h via cron
# 0 22 * * 1-5 /opt/trading/daily_report.sh

REPORT_DIR="/opt/trading/reports"
DATE=$(date +%Y-%m-%d)

# 1. Extraire les données du jour
psql -h localhost -U trader trading -c "
  SELECT strategy,
         SUM(CASE WHEN side='sell' THEN quantity*price
                  WHEN side='buy' THEN -quantity*price END) AS pnl,
         COUNT(*) AS trades
  FROM trades
  WHERE time::date = CURRENT_DATE
  GROUP BY strategy
  ORDER BY pnl DESC;
" -o "${REPORT_DIR}/${DATE}_pnl.txt"

# 2. Demander à Claude Code de rédiger le rapport
claude -p "Lis ${REPORT_DIR}/${DATE}_pnl.txt et génère un résumé
Discord-friendly (markdown, emojis) du P&L du jour.
Inclus : P&L total, meilleure/pire stratégie, nombre de trades,
et une recommandation pour demain." > "${REPORT_DIR}/${DATE}_report.md"

# 3. Envoyer sur Discord via webhook
CONTENT=$(cat "${REPORT_DIR}/${DATE}_report.md")
curl -H "Content-Type: application/json" \
     -d "{\"content\": \"${CONTENT}\"}" \
     "https://discord.com/api/webhooks/VOTRE_WEBHOOK"

Avertissements importants

Les agents autonomes sont des outils d'automatisation de monitoring, PAS des bots de trading :

  • JAMAIS d'exécution de trades — un agent ne doit jamais passer d'ordres sur le marché
  • Risque de prompt injection — si l'agent lit des données externes (news, chat), un attaquant pourrait manipuler ses actions
  • Principe du moindre privilège — l'agent n'a accès qu'aux données en lecture, jamais aux clés API broker
  • Logs de chaque action — tout ce que fait l'agent est loggé et auditable

Flux de données expliqué étape par étape

  1. Exécution d'un trade : votre stratégie envoie un ordre au broker et enregistre le trade dans TimescaleDB + notifie Discord via webhook
  2. Mise à jour des métriques : après chaque cycle, la stratégie écrit les métriques custom dans le fichier .prom (positions, P&L, drawdown)
  3. Collecte Prometheus : toutes les 15 secondes, Prometheus scrape Node Exporter (système + métriques custom)
  4. Évaluation des règles : Prometheus compare les métriques aux seuils définis dans alert_rules.yml
  5. Alerte : si un seuil est dépassé, Alertmanager route l'alerte vers le bon canal Discord selon la sévérité
  6. Visualisation : Grafana affiche en temps réel les données de Prometheus (système) et TimescaleDB (trading)
  7. Analyse : périodiquement, Claude Code analyse les logs et génère des rapports post-mortem

Conseil : commencez en paper trading

Déployez d'abord votre stack complet en mode paper trading (simulation). Alimentez TimescaleDB avec des trades simulés pendant 2 semaines. Cela vous permet de tester vos dashboards, affiner vos seuils d'alerte, et découvrir les problèmes avant de risquer de l'argent réel. La majorité des traders qui perdent de l'argent n'ont jamais testé leur infrastructure en conditions réelles.
