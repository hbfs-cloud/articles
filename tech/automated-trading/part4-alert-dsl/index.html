Why Build a DSL?

Hardcoding alert conditions in scripts means every change requires code edits, testing, and deployment. A DSL gives you:

  • Composability: Combine conditions with AND/OR logic like building blocks
  • Readability: rsi(14) crosses_above 30 AND volume > avg * 2 is self-documenting
  • Evolution: Add new condition types without rewriting the engine
  • Backtesting: Run the same conditions against historical data to validate
  • User-editable: Change alert conditions via Discord commands without touching code

The market-alerts MCP server provides 7 tools: create_alert, list_alerts, update_alert, delete_alert, pause_alert, snooze_alert, get_alert_status.

Full Grammar (EBNF)

alert_dsl.ebnf
alert       := condition (("AND" | "OR") condition)*
condition   := "NOT"? atom | "(" alert ")" | quantifier
atom        := field operator value
quantifier  := ("ALL_OF" | "ANY_OF") "(" alert ("," alert)* ")"
             | "N_OF" "(" number "," alert ("," alert)* ")"
field       := "price" | "volume" | "rsi" "(" number ")"
             | "macd" | "signal" | "macd_histogram"
             | "ema" "(" number ")" | "sma" "(" number ")"
             | "bb_width" | "bb_squeeze" | "atr" "(" number ")"
             | "pe_ratio" | "earnings_in_days" | "short_interest"
             | "stocktwits_bull_ratio" | "reddit_mentions_24h"
             | "news_sentiment" | "insider_buying_90d"
             | "relative_volume" | "volume_surge"
operator    := ">" | "<" | ">=" | "<=" | "==" | "!="
             | "crosses_above" | "crosses_below"
             | "within_range" | "IN"
value       := number | string | field | function_call
function_call := ("sma" | "ema" | "avg" | "max" | "min"
                | "percentile" | "sector_avg") "(" args ")"
number      := [0-9]+ ("." [0-9]+)? ("%")?
string      := '"' [^"]* '"'

Setup Confirmation State Machine

Alerts don't just fire once. They track a setup through multiple states from initial detection to confirmation to execution.

State Machine Logic
function evaluateSetupState(conditions, currentData) {
  const total = conditions.length;
  const met = conditions.filter(c => evaluate(c, currentData)).length;
  const ratio = met / total;

  if (ratio === 0) return "EXPIRED";      // No conditions met
  if (ratio < 0.5) return "WATCHING";      // Less than half
  if (ratio < 0.75) return "FORMING";      // More than half
  if (ratio < 1.0) return "NEAR_CONFIRMED"; // Almost all
  if (ratio === 1.0) return "CONFIRMED";    // All conditions met!

  // After CONFIRMED, wait for entry trigger
  if (state === "CONFIRMED" && entryTriggered(currentData)) {
    return "TRIGGERED"; // Send alert + create trade log
  }
}

// Partial match reporting
function getPartialReport(conditions, currentData) {
  return conditions.map(c => ({
    condition: c.toString(),
    met: evaluate(c, currentData),
    currentValue: getCurrentValue(c.field, currentData),
    targetValue: c.value,
    progress: calculateProgress(c, currentData) // 0-100%
  }));
}

Why State Tracking Matters

Instead of binary "fired/not fired" alerts, the state machine lets you see setups forming. When 5 out of 6 conditions are met, you can prepare. When the last condition fires, you're ready to act instantly. This is the difference between retail and institutional execution quality.

Post-Scanner Alert Pipeline
// After scanner identifies 10 A+ setups:
for (const setup of scannerResults) {
  create_alert({
    name: `${setup.ticker} ${setup.strategy}`,
    symbol: setup.ticker,
    conditions: generateConditions(setup),
    actions: [
      setup.grade === "A++" ? "discord_notify:#priority-alerts" : "discord_notify:#trading-signals",
      "log_setup"
    ],
    expiry: addDays(today, setup.horizon === "swing" ? 10 : 30),
    priority: setup.grade === "A++" ? "critical" : "high",
    metadata: {
      entry: setup.entry,
      stop: setup.stop,
      tp1: setup.tp1,
      tp2: setup.tp2,
      rr: setup.rr,
      compositeScore: setup.composite,
      grade: setup.grade,
      scanDate: today
    }
  });
}

function generateConditions(setup) {
  switch (setup.strategy) {
    case "oversold_bounce":
      return `rsi(14) crosses_above 30 AND price > ${setup.entry * 0.98}
              AND volume > avg_volume * 1.3`;
    case "momentum_breakout":
      return `price crosses_above ${setup.entry}
              AND volume > avg_volume * 1.5 AND rsi(14) > 55`;
    case "safe_haven":
      return `price > ema(20) AND vix > 25`;
    default:
      return `price within_range(${setup.entry * 0.98}, ${setup.entry * 1.02})
              AND volume > avg_volume`;
  }
}

Managing Alert Lifecycle

// List all active alerts
list_alerts({ status: "active" })

// Pause during earnings blackout
pause_alert({ id: "alert_7f8a9b2c", reason: "AAPL earnings tomorrow" })

// Snooze for 24 hours (e.g., FOMC day)
snooze_alert({ id: "alert_7f8a9b2c", duration: "24h" })

// Check specific alert status
get_alert_status({ id: "alert_7f8a9b2c" })
// → { state: "NEAR_CONFIRMED", met: 4, total: 5, lastCheck: "..." }

// Update conditions (e.g., tighten after partial move)
update_alert({
  id: "alert_7f8a9b2c",
  conditions: "price crosses_above 193 AND volume > avg_volume * 1.3"
})

// Delete expired or irrelevant alerts
delete_alert({ id: "alert_7f8a9b2c" })
