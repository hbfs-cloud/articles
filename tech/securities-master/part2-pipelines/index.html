High-Velocity Ingestion:
Meltano Taps in Go & Nomad

Forget slow Python scripts. We challenge conventional wisdom by modeling true institutional references (Equities, Futures, IRS, Crypto) and orchestrating high-concurrency Singer extractors directly natively in HashiCorp Nomad.

In Part 1, we defined what a point-in-time correct architecture looks like. But looking directly into tier-1 hedge fund codebases—such as a reference-service and execution-instruments repository—reveals that our initial perimeter was too narrow.

A true hedge-fund instrument suite does not solely support stocks. It natively models EQUITY, ETF, FUTURE, FUTURES_SPREAD, INDEX, RATE, FXFORWARD, IRS, OPTIONVOL, and CRYPTO. It deals with diverse SettlementTypes, MarketDataSourceTypes, and extremely granular OMS constraints like skip_start_of_day_position for accounts or execution routing to specific Prime Brokers.

If you aim to model this massive universe across multiple providers (Yahoo, StockAnalysis, Casablanca Bourse, Binance, FRED), relying on standard Python ELT loops or Airbyte connections will fail either on speed, rate-limiting nuances, or memory exhaustion.

Our solution: Write a Custom Go Extractor obeying the Singer Specification, capable of highly concurrent ingestion, and orchestrate the raw data-dump straight into PostgreSQL using Meltano and HashiCorp Nomad.

The Raw PostgreSQL Schema

Before launching our ingestion, we configure our PostgreSQL destination (securities_master.raw_zone). We draw inspiration directly from robust OMS journaling and reference structures. Everything is dumped globally; transformations are left for dbt in Part 3.

-- raw_zone.instruments
CREATE TABLE raw_instruments (
    external_id VARCHAR(100),       -- Provider's specific ID (e.g. BVC Drupal ID or Yahoo Ticker)
    provider_name VARCHAR(50),      -- 'YAHOO', 'BVC', 'STOCKANALYSIS'
    symbol VARCHAR(50), 
    isin VARCHAR(12),
    
    -- We extract precisely as the provider defines it, e.g. 'EQUITY', 'CRYPTO', 'OPTIONVOL'
    instrument_type VARCHAR(50), 
    
    -- Metadata payload
    raw_payload JSONB,              
    
    ingested_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- raw_zone.market_data
CREATE TABLE raw_market_data (
    provider_name VARCHAR(50) NOT NULL,
    symbol VARCHAR(50) NOT NULL,
    trade_date TIMESTAMP WITH TIME ZONE NOT NULL,
    
    open_price NUMERIC(20, 8),
    high_price NUMERIC(20, 8),
    low_price NUMERIC(20, 8),
    close_price NUMERIC(20, 8),
    adj_close NUMERIC(20, 8),
    volume NUMERIC(20, 8),
    
    ingested_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    
    PRIMARY KEY (provider_name, symbol, trade_date)
) PARTITION BY LIST (EXTRACT(YEAR FROM trade_date));
-- Note: Sub-partitioning per provider is recommended for massive datasets.

Custom Meltano Tap in Go

Go’s concurrency model is unmatched for IO-bound work like fetching thousands of tickers simultaneously. To integrate smoothly with the Modern Data Stack, we make Go speak the Singer Protocol. It communicates with Meltano purely through stdout using JSON messages: SCHEMA (to define the table structure), STATE (for incremental bookmarks), and RECORD (the actual data).

// main.go - Meltano Tap in Go (tap-marketdata)
package main

import (
	"encoding/json"
	"fmt"
	"os"
	"sync"
	"time"
)

type SingerMessage struct {
	Type   string      `json:"type"`
	Record interface{} `json:"record,omitempty"`
	Schema interface{} `json:"schema,omitempty"`
	Stream string      `json:"stream,omitempty"`
}

type OHLCVRecord struct {
	Symbol      string  `json:"symbol"`
	TradeDate   string  `json:"trade_date"`
	OpenPrice   float64 `json:"open_price"`
	HighPrice   float64 `json:"high_price"`
	LowPrice    float64 `json:"low_price"`
	ClosePrice  float64 `json:"close_price"`
	AdjClose    float64 `json:"adj_close,omitempty"`
	Volume      float64 `json:"volume"`
	ProviderName string `json:"provider_name"`
}

func emitRecord(stream string, record interface{}) {
	msg := SingerMessage{ Type: "RECORD", Stream: stream, Record: record }
	b, _ := json.Marshal(msg)
	fmt.Println(string(b))
}

func main() {
	// First: Emit SCHEMA for target-postgres to build the table dynamically
	emitSchema()

	providers := []string{"YAHOO", "BINANCE", "BVC", "STOCKANALYSIS"}

	// High-Concurrency Fetching (adjust semaphore based on provider limits)
	const maxConcurrency = 50
	sem := make(chan struct{}, maxConcurrency)
	var wg sync.WaitGroup

	for _, provider := range providers {
	    symbols := getUniverseForProvider(provider)
        for _, sym := range symbols {
            wg.Add(1)
            go func(p string, s string) {
                defer wg.Done()
                sem <- struct{}{}
                defer func() { <-sem }()

                bars := FetchProviderData(p, s) 

                for _, bar := range bars {
                    // Emit raw row formatted for target-postgres
                    emitRecord("raw_market_data", OHLCVRecord{
                        Symbol:       s,
                        TradeDate:    bar.Date.Format(time.RFC3339),
                        OpenPrice:    bar.Open,
                        HighPrice:    bar.High,
                        LowPrice:     bar.Low,
                        ClosePrice:   bar.Close,
                        AdjClose:     bar.AdjClose,
                        Volume:       bar.Volume,
                        ProviderName: p,
                    })
                }
            }(provider, sym)
        }
    }

	wg.Wait()
	os.Exit(0)
}

The Nomad Scheduling Job

The beauty of the Modern Data Stack is decoupling. We don't need a heavy Airflow deployment for this. HashiCorp Nomad is incredibly elegant for running batch or periodic Meltano ELT jobs at the end of the trading day.

Here is the exact Nomad Job specification we deploy to run our ingestion nightly. It pulls our custom Docker image containing the compiled Go binary + Meltano, injects the secrets required for PostgreSQL via Vault, and kicks off meltano run.

# marketdata-ingest.nomad.hcl

  datacenters = ["dc1"]
  type        = "batch"
