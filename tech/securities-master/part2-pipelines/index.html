Custom Data Pipelines & Impeccable DB Schema

Moving away from black-box ELT tools, we write highly concurrent Go parsers inspired by leading hedge fund architectures to ingest data from Yahoo, Casablanca Bourse, and more into a bulletproof SCD Type 2 PostgreSQL database.

In Part 1, we laid out the foundational rules of point-in-time correctness. But how do we actually move the massive daily dumps of static data, closing prices, and company metadata from external APIs into our pristine data warehouse?

While tools like Airbyte or Meltano are fantastic for standard SaaS integrations (like pulling Salesforce contacts), market data requires extreme control over rate limits, caching, and concurrency. A large hedge fund handling reference data typically builds a bespoke reference-service (often in Java or Go) to fetch, normalize, and resolve entities.

1. The "Nickel" Database Schema

Before writing a single line of ingestion code, the primary database schema must be perfect. We blend our point-in-time concepts with real-world institutional models (like the Instrument and TradableInstrument interfaces found in Brevan Howard or Citadel architectures).

A true institutional master separates Reference Data (the instrument metadata) from Market Data (the prices). Crucially, the Reference table implements Slowly Changing Dimensions (SCD) Type 2 with absolute precision via valid_from and valid_to constraints.

-- 1. The Reference Data Master Table (SCD Type 2)
CREATE TABLE instruments (
    -- Surrogate system ID (e.g., UUID or internal sequence)
    internal_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- Identifier types
    symbol VARCHAR(50) NOT NULL,
    ric VARCHAR(50),             -- Reuters Instrument Code
    bbg_id VARCHAR(50),          -- Bloomberg Global ID
    isin VARCHAR(12),            -- ISIN Code
    figi VARCHAR(12),            -- Financial Instrument Global Identifier
    
    -- Classifications
    instrument_type VARCHAR(20) NOT NULL,    -- EQUITY, ETF, FX_FORWARD, CRYPTO
    exchange_code VARCHAR(20),               -- NYS, PAR, CAS
    currency_code VARCHAR(3) NOT NULL,       -- USD, MAD, EUR
    
    tick_size NUMERIC(15, 6),
    is_tradable BOOLEAN DEFAULT TRUE,
    
    -- Point-in-time constraints (SCD2)
    valid_from TIMESTAMP WITH TIME ZONE NOT NULL,
    valid_to TIMESTAMP WITH TIME ZONE NOT NULL,
    
    -- Prevents overlapping timeframes for the same ISIN/exchange combo
    EXCLUDE USING gist (
        isin WITH =, 
        exchange_code WITH =, 
        tstzrange(valid_from, valid_to) WITH &&
    )
);

-- 2. The Market Data Table (Partitioned by Month)
CREATE TABLE market_data_ohlcv (
    instrument_id UUID REFERENCES instruments(internal_id),
    trade_date DATE NOT NULL,
    
    open_price NUMERIC(15, 6),
    high_price NUMERIC(15, 6),
    low_price NUMERIC(15, 6),
    close_price NUMERIC(15, 6) NOT NULL,
    adj_close NUMERIC(15, 6),
    volume BIGINT,
    
    data_source VARCHAR(30) NOT NULL, -- e.g., 'YAHOO', 'BVC', 'STOCKANALYSIS'
    
    PRIMARY KEY (instrument_id, trade_date, data_source)
) PARTITION BY LIST (EXTRACT(YEAR FROM trade_date));
-- Note: Further monthly sub-partitioning is highly recommended for production scale.

Notice the EXCLUDE USING gist constraint. It mathematically prevents any overlaps. You can never have two rows for the same instrument active at the identical millisecond.

2. Data Sources & The Provider Model

Our ingestion system (modeled internally as a Provider) manages state, caching, and look-ahead bias across drastically different endpoints.

The Yahoo Finance Pipeline (High Concurrency)

Yahoo Finance serves as an incredible free fallback for historical data and macro indices (e.g., ^GSPC, ^VIX). However, downloading thousands of tickers sequentially is too slow. We use Go's massive concurrency model with a semaphore to bound the HTTP requests.

// internal/ohlcv/yahoo.go (Excerpt)
func (p *Provider) loadSymbols(symbols []string, timeframe string) error {
	const maxConcurrency = 50 // Bounded concurrency
	sem := make(chan struct{}, maxConcurrency)
	var wg sync.WaitGroup

	for _, symbol := range symbols {
		wg.Add(1)
		go func(sym string) {
			defer wg.Done()
			
			// Acquire semaphore
			sem <- struct{}{}
			defer func() { <-sem }()

			// 1. Smart Check: Does a fresh cache exist for this exact date?
			if cacheFile := p.findLatestCache(sym, timeframe); cacheFile != "" {
				bars, _ := LoadOHLCVFromCSV(cacheFile)
				p.data[sym] = filterBarsByDateRange(bars) // Prevent look-ahead bias
				return
			}

			// 2. Fetch if not found or stale
			bars, err := FetchHistoryYahooJSON(sym, timeframe)
			if err == nil {
				p.data[sym] = filterBarsByDateRange(bars)
			}
		}(symbol)
	}

	wg.Wait()
	return nil
}

The Casablanca Bourse (BVC) Pipeline (Rate-limited, JSON:API)

Frontier and emerging markets often provide data through completely custom APIs. The Casablanca Bourse (BVC), for instance, uses a Drupal backend with a strict JSON:API structure. Ingestion here is completely different from Yahoo. It requires pagination extraction and strict rate limiting to avoid getting banned.

// internal/staticdata/bvc.go (Excerpt)
func fetchBVCInstruments() (map[string]BVCInstrument, error) {
	instruments := make(map[string]BVCInstrument)
	url := "https://api.casablanca-bourse.com/fr/api/bourse_data/instrument?page[limit]=200"

	for url != "" {
		req, _ := http.NewRequest("GET", url, nil)
		resp, _ := client.Do(req)
		
		var result bvcInstrumentResponse
		json.NewDecoder(resp.Body).Decode(&result)

		for _, rec := range result.Data {
			attr := rec.Attributes
			instruments[attr.Symbol] = BVCInstrument{
				Symbol:       attr.Symbol,
				InstrumentID: attr.DrupalInternalID, // Required for their specific OHLCV queries
				ISIN:         attr.CodeISIN,
			}
		}

		// Handle Drupal JSON:API Pagination
		if result.Links.Next != nil {
			url = result.Links.Next.Href
			time.Sleep(200 * time.Millisecond) // Gentle rate limiting
		} else {
			url = ""
		}
	}
	return instruments, nil
}

3. Local Disk Caching as a Resilience Layer

Writing directly to the database during high-concurrency loops (like fetching 5,000 tickers from Yahoo) can cause severe database locking and connection pool exhaustion. Instead, a robust securities master implements a Spill-to-Disk Cache Strategy.

When our Yahoo worker fetches JSON, it immediately dumps it as an optimized .csv to a local date-folder (e.g., cache/yahoo/2026-02-24/1d/AAPL.csv). A secondary, asynchronous worker pool reads these CSVs when they are ready and executes bulk COPY commands into the PostgreSQL `market_data_ohlcv` table.

Data Ingestion Takeaways

  • Design strictly: Map real-world abstractions (InstrumentType, Time-Travel validity constraints) into PostgreSQL natively using GIST indices.
  • Be mindful of API limits: Distinguish between endpoints that can sustain concurrent hits (Yahoo) vs fragile local endpoints (BVC).
  • Decouple fetchers from writes: Dump API responses to disk first, then load them entirely deterministically into the database.
