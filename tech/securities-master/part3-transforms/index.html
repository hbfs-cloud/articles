Now, we face the chaos.

Our raw_zone schema is overflowing with raw JSON. The Casablanca Bourse API spits out nested, undocumented properties. Yahoo Finance dumps flat CSVs. Binance APIs disagree on ticker conventions (is it BTC-USD or BTCUSDT?). If a quant researcher queries this directly, your hedge fund will hemorrhage capital due to bad data. To bridge the gap between unstructured API sludge and pristine, mathematically sound predictive models, we implement a hardened Medallion Architecture using dbt (Data Build Tool).

The Architectural Strategy

The Medallion Logic in Quantitative Finance

The Medallion pattern (Bronze, Silver, Gold) isn't just a buzzword; it's a defensive engineering mechanism. It isolates the chaos of external providers from the fragile logic of your trading algorithms.

Bronze: Raw & Cast

Materialization: view or ephemeral

This layer applies "Schema-on-Read". It reaches into the JSON payloads, extracts keys using JSON path functions, casts them to rigorous PostgreSQL types (e.g., NUMERIC(14,4)), and normalizes column names across providers. Zero storage cost.

Silver: Cleansed & Historicized

Materialization: incremental & snapshot

The source of truth. Deduplication, resolution of conflicting provider data, and temporal tracking. This is where we implement SCD Type 2 to track precisely when Apple changed its GICS Sector, and where we merge billions of daily OHLCV bars incrementally.

Gold: AI & Strategy Marts

Materialization: table

Highly denormalized Star Schemas. We pre-calculate technical indicators (ATR, Rolling Volatility, Dollar Volume). A quantitative agent or BI tool queries the Gold layer to find trading candidates instantly, without writing complex joins or point-in-time window functions.

Layer 1: Bronze

Bronze: Taming the JSON Sludge

We never write INSERT statements with JSON parsing. Instead, we define dbt views over the raw tables. If an API provider changes their payload structure tomorrow (e.g., Yahoo changes Adj Close to adjusted_close), we only update the Bronze view. The entire downstream pipeline remains protected.

Here is how we extract deeply nested instrument reference data from a notoriously undocumented exchange API, the Casablanca Bourse (BVC).

dbt sql — models/bronze/stg_bvc_instruments.sql
{{ config(
    materialized='view',
    tags=['bronze', 'reference_data']
) }}

WITH raw_bvc AS (
    SELECT * FROM {{ source('raw_zone', 'raw_instruments') }}
    WHERE provider_name = 'BVC'
),

extracted AS (
    SELECT
        -- The Meltano metadata
        _sdc_extracted_at AS ingested_at,
        
        -- PostgreSQL JSONB Extraction & Casting
        external_id::VARCHAR(50) AS provider_tick,
        (raw_payload->>'codeISIN')::CHAR(12) AS isin,
        (raw_payload->>'instrumentName')::TEXT AS name,
        
        -- Dealing with nested JSON arrays (e.g., sector classifications)
        jsonb_array_element_text(raw_payload->'sectors', 0)::TEXT AS sector_primary,
        
        -- Standardizing to our Institutional Part 1 Data Model
        'EQUITY'::VARCHAR(50) AS instrument_type,
        'MAD'::CHAR(3) AS currency,
        TRUE AS is_tradable
        
    FROM raw_bvc
)

-- Defensive Deduplication: 
-- Sometimes an API pagination bug causes Meltano to ingest the same ticker twice in one run.
SELECT *
FROM extracted
QUALIFY ROW_NUMBER() OVER (PARTITION BY isin ORDER BY ingested_at DESC) = 1

The QUALIFY ROW_NUMBER() Pattern

Data ingestion is inherently flawed. Network timeouts lead to retries, which lead to duplicated records in the raw_zone. Instead of relying on DISTINCT (which is computationally expensive and blind to timestamps), we use window functions. QUALIFY ROW_NUMBER() OVER (... ORDER BY ingested_at DESC) = 1 guarantees we strictly take the absolutely most recent payload for a given instrument, cleanly discarding duplicates.

Layer 2: Silver (Time-Series)

Incremental Models: Processing Billions of Bars

If you have 10,000 global equities, 25 years of daily history is roughly 60+ million rows. If you query intraday (1-minute bars), you are swiftly dealing with tens of billions of rows. Materializing this as a table in dbt—which runs a DROP TABLE then CREATE TABLE every time—will bring your database cluster to its knees.

We use dbt's incremental materialization. On the first run, it builds the entire table. On every subsequent run, dbt intelligently executes an INSERT ... ON CONFLICT or a MERGE statement, processing only the new data.

dbt sql — models/silver/fct_market_data_daily.sql
{{ config(
    materialized='incremental',
    unique_key=['symbol', 'trade_date'],
    -- We leverage the partition strategy defined in Part 1!
    partition_by={'field': 'trade_date', 'data_type': 'date', 'granularity': 'month'}
) }}

WITH combined_bronze_bars AS (
    SELECT * FROM {{ ref('stg_yahoo_bars') }}
    UNION ALL
    SELECT * FROM {{ ref('stg_bvc_bars') }}
    UNION ALL
    SELECT * FROM {{ ref('stg_binance_bars') }}
)

SELECT
    symbol,
    trade_date,
    open_price,
    high_price,
    low_price,
    close_price,
    volume,
    -- Calculate VWAP if the provider didn't supply it
    COALESCE(vwap, (high_price + low_price + close_price) / 3) AS vwap_proxy,
    ingested_at
FROM combined_bronze_bars

{% if is_incremental() %}
    -- This block ONLY runs on daily pipeline updates
    -- It asks: "What is the maximum date currently in this table?"
    -- And then only selects rows from the Bronze views strictly newer or equal to that date.
    WHERE trade_date >= (SELECT MAX(trade_date) - interval '3 days' FROM {{ this }})
{% endif %}

The Lookback Window (- interval '3 days')

Why do we look back 3 days instead of just grabbing > MAX(trade_date)? Because of late-arriving data and corrections. Sometimes, an exchange revises the closing volume of Friday on a Monday morning. By defining unique_key=['symbol', 'trade_date'], dbt knows how to gracefully upsert (update if exists, insert if not). Scanning a 3-day trailing window guarantees we catch silent api corrections while processing 99.9% less data than a full refresh.

Layer 2: Silver (SCD Type 2)

Automating SCD Type 2 with dbt Snapshots

In Part 1, we defined a rigorous framework: when fundamental metadata changes (e.g., Apple changes its GICS sector, or a ticker symbol is renamed due to a merger), we must not overwrite the row. We must close the valid_to timestamp of the old record, and insert a new record with valid_from set to now. Hand-coding these SQL merges is famously bug-prone.

We outsource this entirely to dbt Snapshots.

dbt snapshot — snapshots/dim_instruments_snapshot.sql
{% snapshot dim_instruments_snapshot %}

{{
    config(
      target_schema='silver_zone',
      unique_key='isin',

      -- Strategy: 'check' means dbt compares specific columns to detect a mutation
      strategy='check',
      check_cols=['name', 'sector', 'industry', 'instrument_type', 'is_tradable'],
    )
}}

SELECT
    isin,
    symbol,
    name,
    instrument_type,
    sector,
    industry,
    currency,
    is_tradable
FROM {{ ref('stg_all_instruments') }}

{% endsnapshot %}

How it works: dbt takes a hash of the check_cols. Tomorrow, when the Airflow DAG runs dbt snapshot, dbt compares the incoming API payload against the existing rows in silver_zone.dim_instruments_snapshot.

  • If the hash matches, dbt does nothing.
  • If a new isin appears, dbt inserts it with dbt_valid_from = current_timestamp and dbt_valid_to = NULL.
  • If Apple's sector changed to "AI Technologies", dbt issues an UPDATE statement to set the old Apple row's dbt_valid_to = current_timestamp, and INSERTs the new version.

This magically generates the exact institutional Point-in-Time architecture we designed in SQL in Part 1!

Data Quality Assurance

Trusting the Data via Automated Tests

If you feed NaN values to a Python backtester, it crashes. If you feed bad data to a live trading algorithm, it buys bad assets. We use dbt's testing assertions as a strict CI/CD gate. Data does not reach the Gold layer if tests fail.

yaml — models/silver/schema.yml
models:
  - name: fct_market_data_daily
    description: "Daily OHLCV bars. The core time-series of the Securities Master."
    columns:
      - name: symbol
        tests:
          - not_null
      - name: trade_date
        tests:
          - not_null
      - name: close_price
        tests:
          - not_null
          # A custom dbt_expectations test: Price cannot be negative or zero.
          - dbt_expectations.expect_column_values_to_be_between:
              min_value: 0.0001 
              
  - name: dim_instruments_snapshot
    columns:
      - name: instrument_type
        tests:
          # Reject the pipeline if a provider invents a new undocumented asset class
          - accepted_values:
              values: ['EQUITY', 'FUTURE', 'FXFORWARD', 'IRS', 'OPTIONVOL', 'CRYPTO']
Layer 3: Gold (Analytical Marts)

Gold: The AI Strategy Discovery Mart

The Silver layer is perfectly structured, normalized time-series data. However, asking a Data Scientist or an LLM to dynamically write window functions to calculate 20-day Average True Ranges (ATR) across historical SCD2 dimensions is masochistic.

The Gold layer drops normalization. We use dbt to pre-compute massive, wide "Star Schema" tables (Marts) optimized solely for rapid SELECT queries. When your systematic scanner runs every morning to find "Highly Liquid, High Volatility Breakout Candidates", it hits the Gold layer.

dbt sql — models/gold/mart_strategy_universe.sql
{{ config(
    materialized='table',
    tags=['gold', 'ai_marts']
) }}

WITH active_instruments AS (
    -- Hide SCD2 complexity from downstream users!
    -- We only expose WHAT is currently tradable today.
    SELECT * FROM {{ ref('dim_instruments_snapshot') }}
    WHERE dbt_valid_to IS NULL 
      AND is_tradable = TRUE
),

volatility_and_liquidity AS (
    SELECT
        symbol,
        trade_date,
        close_price,
        
        -- Liquidity: 20-Day Average Daily Volume (in Dollars)
        AVG(volume * close_price) OVER w_20d AS adv_20d_usd,
        
        -- Volatility: 20-Day Realized Volatility (Standard Deviation)
        STDDEV(close_price) OVER w_20d AS realized_vol_20d,
        
        -- Momentum: 50-Day Simple Moving Average
        AVG(close_price) OVER w_50d AS sma_50d

    FROM {{ ref('fct_market_data_daily') }}
    
    WINDOW 
        w_20d AS (PARTITION BY symbol ORDER BY trade_date ROWS BETWEEN 20 PRECEDING AND CURRENT ROW),
        w_50d AS (PARTITION BY symbol ORDER BY trade_date ROWS BETWEEN 50 PRECEDING AND CURRENT ROW)
)

-- Build the final wide analytical table
SELECT
    ref.isin,
    ref.symbol,
    ref.name,
    ref.sector,
    metrics.trade_date,
    metrics.close_price,
    metrics.adv_20d_usd,
    metrics.realized_vol_20d,
    metrics.sma_50d,
    
    -- AI Tagging: Pre-classify regimes
    CASE 
        WHEN metrics.close_price > metrics.sma_50d THEN 'Bullish'
        ELSE 'Bearish'
    END AS trend_regime

FROM active_instruments ref
JOIN volatility_and_liquidity metrics ON ref.symbol = metrics.symbol
-- Implement strict retail/institutional liquidity filters at the mart level
WHERE metrics.adv_20d_usd > 2000000

Because this is materialized as a table, the complex window functions are computed once during the Airflow nightly batch. When generating an Evidence.dev dashboard or prompting an AI assistant via MCP, retrieving the top momentum candidates takes under 10 milliseconds.

Conclusion & Next Steps

  • Bronze Views decouple our database from API schema changes, standardizing JSON payloads natively.
  • Incremental Logic with late-arriving overlap windows allows us to process 60M+ rows in seconds, merging only newly fetched data while correcting historical API errors.
  • dbt Snapshots mathematically automate SCD Type 2 tracking. Overwrites are abolished; full historical lineage of reference data is guaranteed.
  • Gold Marts pre-compute computational heavy lifting (Volatility, Adv, Regimes) via WINDOW functions, exposing pristine interfaces for Systematic Agents.

The underlying data is now structured and validated. But the math is still wrong. If Apple does a 4-for-1 stock split tomorrow, our chart will show a 75% market crash.
