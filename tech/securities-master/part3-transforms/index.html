Transforms: The Medallion Architecture

Our raw PostgreSQL schemas are overflowing with raw JSON from Yahoo and BVC. Now, we use dbt to orchestrate an impeccable Bronze → Silver → Gold architecture. It's time to normalize identifiers, apply SCD Type 2 logic, build incremental models, and expose AI-ready strategy marts.

In Part 1, we established the design rules for a robust Securities Master, heavily relying on the concepts of point-in-time correctness, SCD Type 2 tracking, and specific models for instruments types (Equities, Futures, IRS...). In Part 2, we unleashed highly concurrent Go Extractors wrapped in Meltano, filling our raw_zone in PostgreSQL.

Now, we face reality: the data is brutal, unstructured, and disparate. Yahoo tickers look like AAPL or 7203.T, Casablanca API (BVC) returns Drupal-formatted JSON with no standard ISIN verification, and Binance dumps nested arrays. We need a robust mechanism to sanitize, conform, and expose this.

We rely on dbt (Data Build Tool), applying the standard Medallion Architecture adapted specifically for systematic quantitative systems.

The Medallion Data Flow

Bronze Layer

Raw & Unfiltered
1:1 mapping with the raw ingestion tables. Casts JSON to columns. Implemented as pure dbt ephemeral or Light views. Goal: standardize column names.

Silver Layer

Cleansed & Conformed
Resolves duplicates, handles SCD Type 2 historical continuity (valid_from/valid_to). Built using dbt incremental models to handle millions of bars efficiently.

Gold Layer

Business-Ready Marts
Aggregated Star Schema. Optimized for AI strategy discovery, Evidence.dev dashboards, and Point-in-Time Alpha queries. Built as table materialized views.

Bronze: Taming the JSON (Views)

The Bronze layer's entire purpose is to prevent you from ever writing JSONB parsing logic perfectly down the chain. By materializing as a view (or ephemeral), this step costs no storage space in PostgreSQL but drastically sanitizes our SQL development.

Observe how we extract the complex nested Drupal payload from our Casablanca (BVC) extractor.

-- models/bronze/stg_bvc_instruments.sql
{{ config(materialized='view') }}

WITH raw_bvc AS (
    SELECT * FROM {{ source('raw_zone', 'raw_instruments') }}
    WHERE provider_name = 'BVC'
)

SELECT
    external_id AS provider_id,
    -- Extracting specific properties from the JSONB payload
    jsonb_extract_path_text(raw_payload, 'symbol')::VARCHAR(50) AS symbol,
    jsonb_extract_path_text(raw_payload, 'codeISIN')::CHAR(12) AS isin,
    jsonb_extract_path_text(raw_payload, 'instrumentName')::TEXT AS name,
    
    -- Normalizing the classification
    'EQUITY'::VARCHAR(50) AS instrument_type,
    'MAD'::CHAR(3) AS currency,
    
    ingested_at
FROM raw_bvc
-- Basic deduplication on the most recent payload
QUALIFY ROW_NUMBER() OVER (PARTITION BY external_id ORDER BY ingested_at DESC) = 1

Silver: Incremental Loading & SCD Type 2

The Silver layer is the literal engine room of the Securities Master. It receives the standardized data from the Bronze views and locks it into the rigorous rules defined in Part 1.

Handling Millions of Bars Incrementally

When you have 60 million daily bars, recreating the table every run is a catastrophic mistake. dbt Incremental Models allow us to append or merge only the new or updated records since the last successful run.

-- models/silver/fct_market_data.sql
{{ config(
    materialized='incremental',
    unique_key=['provider_name', 'symbol', 'trade_date'],
    partition_by={'field': 'trade_date', 'data_type': 'timestamp', 'granularity': 'year'}
) }}

WITH stg_bars AS (
    SELECT * FROM {{ ref('stg_yahoo_bars') }}
    UNION ALL
    SELECT * FROM {{ ref('stg_bvc_bars') }}
)

SELECT
    provider_name,
    symbol,
    trade_date,
    open_price,
    high_price,
    low_price,
    close_price,
    volume,
    ingested_at
FROM stg_bars

-- The magic dbt Incremental logic
{% if is_incremental() %}
    WHERE trade_date >= (SELECT MAX(trade_date) FROM {{ this }})
{% endif %}

Building SCD Type 2 Snapshots

How do we know if Apple's Sector changed? We don't want to code this manually. dbt ships natively with Snapshots, effectively automating the valid_from and valid_to history tracking.

We create a snapshot configuration for our normalized Reference Data. dbt checks the check_cols (hash of all columns) to detect if a security's taxonomy has mutated, closing the previous valid_to date and opening a new row automatically.

-- snapshots/dim_instruments_scd2.sql
{% snapshot dim_instruments_scd2 %}

{{
    config(
      target_schema='silver_zone',
      unique_key='isin',
      strategy='check',
      check_cols=['name', 'sector', 'industry', 'instrument_type', 'is_tradable'],
    )
}}

SELECT
    symbol,
    isin,
    name,
    instrument_type,
    sector,
    industry,
    currency
FROM {{ ref('stg_unified_instruments') }}

{% endsnapshot %}

This dbt macro generates the exact EXCLUDE USING gist logic and temporal validity chains we defined theoretically in Part 1!

Gold: AI & Strategy Marts (Tables)

The Gold layer drops normalization completely. We construct wide, performant "Marts" specifically optimized for BI tools (Evidence.dev) and downstream quantitative engines.

These models are materialized as tables. They pre-calculate technical indicators, volatility regimes, and liquidity percentiles.

-- models/gold/mart_strategy_discovery.sql
{{ config(materialized='table') }}

WITH latest_reference AS (
    SELECT * FROM {{ ref('dim_instruments_scd2') }}
    WHERE dbt_valid_to IS NULL -- Only currently active instruments!
),
volatility_metrics AS (
    SELECT
        symbol,
        AVG(volume * close_price) OVER (PARTITION BY symbol ORDER BY trade_date ROWS BETWEEN 20 PRECEDING AND CURRENT ROW) AS adv_20d,
        STDDEV(close_price) OVER (PARTITION BY symbol ORDER BY trade_date ROWS BETWEEN 20 PRECEDING AND CURRENT ROW) AS realized_vol_20d
    FROM {{ ref('fct_market_data') }}
)

SELECT
    ref.isin,
    ref.symbol,
    ref.name,
    ref.instrument_type,
    vol.realized_vol_20d,
    vol.adv_20d
FROM latest_reference ref
JOIN volatility_metrics vol ON ref.symbol = vol.symbol
WHERE vol.adv_20d > 1000000 -- Only highly liquid assets

The resulting table, mart_strategy_discovery, is a perfectly clean playground. It guarantees that any ticker listed is actively tradable (no look-ahead biases) and fulfills the liquidity profiles required by your quant engine.

Wrapping Up Part 3

dbt transforms raw API mess into a bulletproof Securities Master:

  • Views shield us from JSON parsing logic.
  • Incremental Models permit updating decades of OHLCV history in seconds.
  • dbt Snapshots automate the brutal SCD Type 2 logic for exact point-in-time correctness.
  • Gold Tables expose data to human analysts and AI Agents without writing crazy JOINs.
