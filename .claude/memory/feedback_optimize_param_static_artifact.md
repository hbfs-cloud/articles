`tools/optimize-param.js` (single-param plateau sweep) evaluates with **static strategy filters** — it ignores `regimeFilters` (the per-regime filter switching the live frozen path uses). Its absolute returns are therefore **artifacts** and routinely overstate a lever.

**Caught 2026-06-16 (balanced underperformance since Apr 20) — THREE layers of artifact, all the way down:**
1. `optimize-param.js` flagged `entryGatePct: 0→2` (+12pp, Sharpe 2.13→3.51). **Artifact** (static filters): the regime-aware validator showed it was actually −5.6% / OOS 0% (rejected most fills → 8 trades).
2. `validate-config-change.js` (regime-aware + OOS) then flagged `early_risk_off+neutral mom_bo→breakout_only` as a real winner: full +6.23%→+10.97%, OOS +7.89%→+8.58%. Applied append-only as v9.0.
3. **But the authoritative `frozen_balanced` (re-sweep) showed NO gain: 51.86% vs 53.28% total, segment −0.17% vs +0.76% — marginally worse.** The validator's absolute baseline (+6.23%) never matched frozen (+53%), so its deltas don't transfer. **Reverted to v8.9 (v9.1-20260616).**

**Conclusion:** balanced's Apr20+ treading water is **regime-structural** (a selective swing-momentum strategy gets chopped in a low-vol grind-up where SPY-beta wins), **not a config bug fixable by single-lever tuning**. No lever survived the authoritative check.

**Why:** every replay/optimizer layer overstates. optimize-param (static filters) > validate-config-change (regime-aware but its own modeling ≠ frozen) > **frozen sweep = the ONLY source of truth**. See [[feedback-regime-aware-eval]], [[feedback-segment-replay-absolute-dd]].

**CORRECTION (2026-06-16, war-room round) — the frozen sweep is NOT the gate for config changes.** `sweep.js` builds `frozen_X` **append-only**: it locks realized historical trades and only re-simulates NEW scans (sweep.js ~line 2313 `newTrades = …newScanDateSet`, ~2454 `frozenTrades = merged`). So a config change applied today moves `frozen_X` by only a sliver (the recent-scan boundary) and reads ≈ baseline **no matter what** — it STRUCTURALLY cannot show a forward config change's merit. Gating on "frozen_X must beat old" is a category error (it's why neutral→breakout AND V6 both "failed" frozen while passing the validator).

**The correct forward test = `validate-config-change.js` (full re-sim of the whole history under the new config + walk-forward OOS).** Trust its OOS *ranking* (not its absolutes). A change is good if it beats CURRENT on full AND OOS there, has a causal mechanism, and aligns with the mandate.

**How to apply — the corrected "process habituel" for a mode config change:**
1. `optimize-param.js --mode X --all --quick` → candidate levers (HYPOTHESES only; static-filter artifacts).
2. `validate-config-change.js` (edit VARIANTS) → regime-aware FULL + OOS. **This is the gate.** Reject anything that loses OOS (overfit: rot=aggressive, horizon5, V10 unconditTrail all won full but lost OOS). Require a causal story.
3. Apply append-only (bump `_version`/`_prevVersion`, append full-modes snapshot to `config-history.json`), re-run `sweep.js` to refresh go-forward. **Do NOT gate on frozen_X** — its tiny move is expected (append-only).
4. The change takes effect **go-forward** (you can't retroactively change locked history anyway). Proof is in forward live results. The validation harness gap (validator absolutes ≠ frozen; frozen can't test forward) is a known DEV todo: build a full-resim harness that matches frozen so config tuning is rigorously testable.
